# Performance baseline — 2026-09-28

Status: baseline for owner review. Proposed budgets are in `perf/budgets.json`
and need one confirmation. Raw results are in [`data/2026-09-28/`](data/2026-09-28/).
How the tooling works is described in [`perf/README.md`](../../perf/README.md).

## Summary

- **Startup is acceptable at today's size, but git status and switching slow down as workspaces grow.**
  - **Tier M** (31 workspaces, like the reference laptop today): the overview is usable at 1.6 s (p50) and 3.1 s (p95), and every proposed budget passes.
  - **Tier L** (50 workspaces × 3 repositories): cards stay fast (2.4 s p95), but git status for all workspaces takes 6.9 s (p95), and a switch between two visited workspaces takes 0.97 s (p95) against a 0.5 s target.
- **Most of the cost is repeated work, not slow code.**
  - The backend starts well over 100 processes at startup: git, editor and assistant detection, and `npx pm2`.
  - It re-reads every session transcript on each request: 213 MiB for one busy workspace.
  - It refetches all of a workspace's data on every switch, even for a workspace visited seconds earlier.
- **Stale-state and robustness defects found.**
  - **D2:** switching workspaces quickly applies the previous workspace's changes and sessions to the one now on screen (rule R3a).
  - **D3:** editor and launch-target detection run CLI probes with no timeout. One blocking CLI leaves those endpoints hanging (observed over 120 s).
  - **D1:** stale Codex session detection, fixed in 2.24.1.
- **Repeatability is not yet within ±10%.** On this laptop (`powersave` governor, CPU around 75 °C), timings drifted up to 2× within one session. Budget checks therefore use a 10% tolerance on p95, and before/after comparisons should alternate builds (A, B, A, B) rather than compare separate sessions.

## Hotspots

| ID | Hypothesis | Verdict | Evidence |
|---|---|---|---|
| H1 | Code panel rescans git every 10 s | **confirmed** | R2b (24 git/min while visible), R1 (12 git/min while hidden) |
| H2 | Session history re-read in full on every request | **confirmed** | R2a; 213 MiB re-read per request at tier L; S5 settles at 1.3 s (p95) at L |
| H3 | Status scan cost grows with workspaces and repos | **confirmed** | 72 git and 600 MiB of header reads per page; status complete at 6.9 s (p95) at L |
| H4 | Unpaged manifest scan, refetch on focus | **refuted (scan)** / inconclusive (focus) | `/api/workspaces` takes 30 ms at 50 workspaces; focus refetch not measured |
| H5 | Background polling | **partly confirmed** | Stops while hidden, except the Code panel (R1). Visible polling only runs with ≤ 24 workspaces. |
| H6 | Bundle parse time | **minor** | Shell drawn 0.45 to 0.65 s after the backend is ready; 3 to 5 long tasks, 0.2 to 0.6 s in total |
| H7 | Detection spawns many processes | **confirmed** | About 25 detection processes per load; `spawn` is the largest CPU cost; unbounded probes cause D3 |

## Defects found

| ID | Defect | Status |
|---|---|---|
| D1 | Codex session cache keyed on the sessions root mtime, so new sessions were missed | Fixed in 2.24.1 (#313) |
| D2 | `fetchGitChanges` and `fetchWorkspaceSessions` (gui/src/App.tsx) apply responses without checking the workspace is still current; the React Query calls also pass no abort signal | Open: rules R3a and R3b |
| D3 | Editor and launch-target detection run `<cli> --version` with no timeout, so a blocking CLI hangs the endpoint | Open: with a fixture HOME, the snap `antigravity --version` never returns (0.7 s with the real HOME) |

## Recommended order for measured-improvement

1. **Fix D2 (stale apply) and pass the abort signal (R3a/R3b).** Correctness first, and low risk.
2. **Session index keyed on file mtime and size (H2, R2a).** Removes the 213 MiB re-read, and should bring S5 and S2/S3 at L within budget.
3. **Code panel: pause when hidden and skip unchanged rescans (H1, R1, R2b).**
4. **Status scan: share one Codex scan across concurrent checks and read headers in small chunks; reuse the PM2 list (H3).** Targets S1 git status complete at L.
5. **Keep switch data warm with `staleTime` for changes and sessions (S3 at L).**
6. **Bound detection probes with a timeout and run them once per process (D3, H7).**

Measure each change with interleaved before/after launches on the same fixture, and add each rule to `perf/rules-enforced.json` once it passes.

## Limits of this baseline

- Timings are from one laptop with thermal drift. The second baseline run on a separate boot is still to do.
- There is no cold-disk measurement and no slow-disk run: both need root.
- Rendering is on the real display. The harness cannot run Electron headless on this build (Chromium's headless mode crashes).
- The `antigravity` hang is caused by the fixture's HOME, so the D3 impact on real machines is inferred from the code, not observed.
- R2b and R1 use the CLI chat's Code panel without a running terminal, since `node-pty` is not built in the worktree.
