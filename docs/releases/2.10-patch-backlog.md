# ContextSpace 2.10 patch backlog

This is a candidate backlog for a possible `2.10.1` patch. It is subject to a
live npm, GitHub Releases, and Marketplace channel check; it is not an announced
or published release.

The backlog is deliberately split into small work packets. Source links point
into this `NexusFlow` worktree, whose product and primary CLI names are now
ContextSpace and `ctxspace`. A ticket may add or adjust tests, implementation,
or documentation only within the paths named in its scope.

## Status and evidence

| Status | Meaning |
| --- | --- |
| **reported awaiting reproduction** | A user report is preserved, but the failure has not been reproduced in the supported runtime matrix. |
| **confirmed code** | Source inspection shows a concrete gap or behavior; runtime verification is still required before release. |
| **verification task** | Existing code is present or the intended behavior is unclear; the ticket first proves the behavior and records any smallest needed adjustment. |

The initial drafting pass was source inspection only, starting from a clean
worktree at `f19420d`. Subsequent implementation and runtime evidence are
recorded under each ticket; the initial environment limitations are historical.
Open verification tasks still require their stated release evidence.

**Next selected fix (2026-09-09): WRK-02.** Protect existing Knowledge/Plan
content and unsaved Knowledge drafts when API calls fail. Live source inspection
confirmed that an error JSON response without `content` currently replaces
content/draft with an empty string, and failed saves lack visible feedback.
This bounded user-content preservation fix takes priority over the remaining
usability work. SEC-01 remains a required dependency review before release;
its runtime impact has not yet been established.

## Batch E — Windows terminal launch and CLI session resumption

### TRM-01 — fix Windows external terminal launching and failure suppression

**Priority:** P1  
**Status:** confirmed code; environment-dependent reproduction

**Evidence:** On a developer machine where Windows Terminal is already open, PowerShell execution policy has been relaxed (`RemoteSigned`/`Unrestricted`), and root-level sessions are launched, the command succeeds in attaching a tab to the visible window. However, source inspection of [`src/utils/terminal-launch.ts`](../../src/utils/terminal-launch.ts#L154-L224) and related server/desktop routes shows that terminal launching fails or suppresses errors under standard end-user / boundary conditions:
1. Fire-and-forget unawaited `execa('wt.exe', ...)` in [`src/utils/terminal-launch.ts`](../../src/utils/terminal-launch.ts#L167-L187): `execa` returns a promise and is not awaited in the synchronous `try` block. Asynchronous spawn failures or non-zero exits are swallowed by `(child as any).catch(() => {})`, immediately returning `{ success: true, command: cmdToRun }`. As a result, the fallback paths (Method 1: `powershell.exe Start-Process` and Method 2: `cmd.exe start`) are unreachable whenever `isBinaryOnPath('wt.exe')` returns true.
2. Execa defaults `windowsHide: true`: Unlike Node's `child_process.spawn` where `windowsHide` defaults to `false`, Execa sets `windowsHide: true` by default. Because neither `execa('wt.exe', ...)` nor `execa('powershell.exe', ...)` sets `windowsHide: false`, terminal processes spawned via Execa on Windows run hidden with no visible console window. Only Method 2 sets `windowsHide: false`, but it is masked by earlier fall-through.
3. Windows Terminal App Execution Alias failure: `isBinaryOnPath('wt.exe')` succeeds via `where.exe` because Windows 10/11 creates an execution alias stub in `%LOCALAPPDATA%\Microsoft\WindowsApps\wt.exe`. Spawning this UWP execution alias via `execa` without `shell: true` frequently fails with Win32 error 1920 or `0x80070002` ("The file cannot be accessed by the system").
4. `-w 0 nt` failure: In `wt.exe`, `-w 0` targets the most recently focused window. When Windows Terminal is not already running or across elevation boundaries (admin vs non-admin), targeting window 0 can fail or be rejected.
5. PowerShell ExecutionPolicy: Globally installed npm CLIs provide both `.ps1` and `.cmd` wrappers. In PowerShell, invoking `${cmdToRun}` resolves `.ps1` first, which fails under default Windows execution policies (`Restricted`/`RemoteSigned`) with `PSSecurityException`. Neither `wt.exe`, `Start-Process`, nor `cmd.exe start` passes `-ExecutionPolicy Bypass`.
6. Path case-sensitivity: In [`src/server.ts`](../../src/server.ts#L348-L357) (`assertWithin`) and [`src/server.ts`](../../src/server.ts#L418) (`resolveExactLaunchWorkspace`), comparisons use case-sensitive `startsWith` and `===`. On Windows where drive letters and path segments are case-insensitive (`C:\` vs `c:\`), mismatches trigger `PathAccessError` (HTTP 400) or workspace resolution failure (HTTP 404).
7. Desktop package PATH on Windows: [`desktop/main.js`](../../desktop/main.js#L289-L294) augments `backendEnv.PATH` only on `darwin`. On Windows, the packaged Electron desktop app inherits an environment that can omit `%APPDATA%\npm`, `%LOCALAPPDATA%\Programs\...`, or `%LOCALAPPDATA%\Microsoft\WindowsApps`.

**Scope:**
1. Await and check Windows Terminal execution in `launchWorkspaceTerminal` for Windows; ensure errors in Windows Terminal correctly fall back to PowerShell `Start-Process` or `cmd.exe start`.
2. Explicitly set `windowsHide: false` on all terminal spawn attempts.
3. Pass `-ExecutionPolicy Bypass` when invoking PowerShell/pwsh to run commands or scripts on Windows.
4. Replace `-w 0 nt` with safe window/tab creation or wrap `wt.exe` via `cmd.exe /c` or fallback if window 0 does not exist.
5. Normalize path casing on Windows in `assertWithin` and `resolveExactLaunchWorkspace`.
6. Augment `desktop/main.js` on Windows with user and npm/WindowsApps path locations.
7. Add unit and mock tests in `src/utils/terminal-launch.test.ts` verifying fallback progression on Windows, explicit `windowsHide: false`, and execution policy flags.

**Acceptance:** Calling `POST /api/workspace/:id/terminal` on Windows opens a visible, focused native terminal window positioned in the requested workspace directory, whether Windows Terminal, PowerShell, or CMD is used. If Windows Terminal fails to spawn or attach, execution cleanly falls back to PowerShell/CMD rather than returning false success. Script commands (`.ps1`) run without execution policy errors.

### SES-01 — fix CLI session resumption across harnesses and worktree boundaries

**Priority:** P1  
**Status:** confirmed code

**Evidence:** Source inspection shows four distinct defects when resuming sessions:
1. Strict UUID enforcement blocks non-UUID session IDs in [`src/server.ts`](../../src/server.ts#L1535) and [`src/utils/terminal-launch.ts`](../../src/utils/terminal-launch.ts#L58): `isValidSessionUuid(sessionId)` restricts session IDs to canonical UUIDv4 format (`/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`). GitHub Copilot session IDs from `~/.copilot/session-store.db` or ACP transports frequently use non-UUID alphanumeric formats (e.g. `ses_...` permitted in `CopilotAcpAdapter.ts#L26`). Clicking "Resume" on a Copilot session returns HTTP 400 `Invalid session UUID format.`
2. Sub-repo worktree directory mismatch on resume: Claude Code stores session transcripts under `~/.claude/projects/<sanitized-path>/<sessionId>.jsonl` ([`src/utils/session-finder.ts`](../../src/utils/session-finder.ts#L46-L57)). Sessions initiated inside a repository worktree (`workspacePath/<repo>`) are stored under that repo's folder. However, [`src/server.ts`](../../src/server.ts#L1549-L1568) always launches the external terminal in `workspacePath` (the root). When `claude --resume <sessionId>` executes in the root, Claude Code fails to locate the session transcript and aborts.
3. Missing frontend resume mapping: In [`gui/src/features/sessions/SessionHistory.tsx`](../../gui/src/features/sessions/SessionHistory.tsx#L49-L62), `getResumeCliCommand` lacks support for `cursor`, falling back to `agy --conversation ${sessionId}`.
4. Unchecked CLI availability on resume: `SessionHistory.tsx` renders an enabled "Resume" button for all discovered sessions even if the corresponding CLI tool is not installed or available on PATH in the current environment.

**Scope:**
1. Support safe non-UUID session IDs in `POST /api/workspace/:id/terminal` and `buildHarnessCliCommand`, using safe character validation (e.g. `isSafeAcpSessionId` / alphanumeric safe format) for Copilot/ACP while preventing shell injection.
2. Record and preserve the originating working directory (`sessionCwd` or sub-repo path) in `AISession` and pass the target working directory to `POST /api/workspace/:id/terminal` so harness resumption (notably Claude Code) launches in the exact folder where the session was recorded.
3. Update `getResumeCliCommand` in `SessionHistory.tsx` to handle `cursor` (`cursor-agent --resume ${sessionId}`).
4. Disable or badge the "Resume" button when the target assistant CLI is not installed/configured on PATH.
5. Add unit tests for non-UUID session ID resumption, sub-repo directory targeting, and cursor command generation.

**Acceptance:** Clicking "Resume" in `SessionHistory` launches an external terminal with the correct working directory and command across all supported assistants (Antigravity, Claude, Codex, Copilot, Cursor). Non-UUID Copilot session IDs are accepted and resumed safely. Sessions recorded inside repository subtrees resume in their respective subtrees without Claude "session not found" errors.

## Release checks and sequencing

Land the batches in this order so each later verification uses the current
desktop identity and GUI error behavior:

1. **Batch A:** icon/runtime packaging, Ubuntu guidance, Linux installed-launch
   smoke, and renamed desktop docs.
2. **Batch B:** theme matrix, real Services reproduction, visible Service errors,
   and stop-state integrity.
3. **Batch C:** Claude reproduction, Plan/refresh semantics, Knowledge/Plan
   recovery, agent-driven Knowledge durability/retrieval, and two-participant
   Workroom review.
4. **Batch D:** dependency security review for the transitive `js-yaml` finding.
5. **Batch E:** Windows terminal launch reliability and CLI session resumption across worktree boundaries.

For each implementation packet, the coordinator records the exact paths,
non-goals, security/data-safety invariants, acceptance evidence, and recovery
step before the single `gpt-5.6-luna`/max writer starts. A `gpt-5.6-sol`/high
planner makes the read-only plan; after the writer freezes the diff, a fresh,
independent `gpt-5.6-sol`/high context reviews correctness, regressions,
boundaries, and missing tests. Only accepted, in-scope findings return to the
same Luna writer; the reviewer never edits the worktree. If role assignment or
a fresh context is unavailable, the gate is blocked rather than silently
claiming acceptance.

The initial backlog drafting pass completed its finite two-revision guard; that
historical guard applies to the backlog document only. Implementation packets
carry their own explicit writer/reviewer guard, including the three-pass guard
recorded for DSK-01a. If a packet remains unresolved at its guard, pause for an
explicit decision instead of silently revising or autoaccepting it.

Before any `2.10.1` release candidate is approved, run the repository gate
`npm test`; run `npm run build:backend` for CLI/server changes and the affected
GUI/desktop E2E suites for UI or packaging changes. Also run
`node scripts/sync-version.mjs --check`, inspect npm/package contents, verify
Windows/Linux packaged install and upgrade evidence, and review a protected-main
PR. Only after the live channel version check and merged review should the
release dispatch described in [`RELEASING.md`](../../RELEASING.md#L32-L76) be
performed. No release dispatch is part of this backlog document.
